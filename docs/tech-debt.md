# 技術的負債の一覧

意図して先送りしたものを、返し忘れないために記録する。Living Document として、負債が増えたとき・返したときに更新する。

## 書き方のルール

- 1 つの負債に 1 つの ID（`TD-001` から連番。返済しても番号は使い回さない）。
- **背景（Why）と今やらない理由（Why not）を必ず書く。** 理由のない負債は、返すときに「なぜこうなっているのか」から調べ直すことになる。
- 「返すきっかけ」は、日付ではなく **起きる出来事** で書く（例: デプロイ先を決めるとき）。
- コードの該当箇所に `// TD-001: ...` のコメントを置き、コードからこの一覧にたどり着けるようにする。
- 返済したら、状態を「返済済み」にし、日付とコミットを書く。節は消さずに残す（判断の履歴になる）。

## TD-001: 本番に /health がない

- 発生: 2026-10-28（コードリーディング Step 2）
- 場所: `src/RoomBooking.ServiceDefaults/Extensions.cs` の `MapDefaultEndpoints`
- 内容: `/health` と `/alive` は `IsDevelopment()` のときだけ公開される。本番（`ASPNETCORE_ENVIRONMENT=Production`）では存在しない。
- 背景（Why）: Aspire のテンプレートの既定。ヘルスチェックの応答には内部の状態（DB に接続できるかなど）が含まれうるため、外部に公開するとリスクがある（`https://aka.ms/aspire/healthchecks`）。
- 今やらない理由（Why not）: デプロイ先が決まっていない。コンテナ基盤によって、ヘルスチェックの叩き方（パス、内部ネットワークだけか）が違うので、今決めても作り直しになる。
- 返すきっかけ: デプロイ先を決めるとき。
- 返し方: コンテナ基盤（Azure Container Apps、Kubernetes など）のヘルスチェックの仕様を確認し、公開する範囲（パス、`/alive` だけか、内部ネットワークだけか）を決める。
- 返済: —
