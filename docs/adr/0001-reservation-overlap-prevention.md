# ADR-0001: 重複予約の防止方式

- ステータス: 提案中
- 日付: 2026-10-23

## 結論

重複予約の禁止は **PostgreSQL の排他制約** で保証する。ドメインは事前チェックとエラーの表現を担い、DB の制約違反はドメインと同じエラーに変換する。

## 背景

- 「同じ会議室で時間帯が重なる予約は登録できない」が、このアプリで最も重要な不変条件である。
- 同時に複数のリクエストが来ても、この不変条件は破られてはならない。
- **日をまたぐ予約が必要**（夜勤、コワーキングスペースのような長時間利用）。そのため「1日」で区切った境界は使えない。
- 時刻は会議室の所在地（日本、夏時間なし）を基準にし、DB には `timestamptz`（UTC の瞬間）で保存する。

## 検討した選択肢

| | A: サービスで判定 + DB 制約 | B: 「会議室 × 日」集約 + 楽観ロック | C: 「日時の区間」で集約を作る |
|---|---|---|---|
| 仕組み | 重なる予約を探して、集約の外で判定する（形は ADR-0002）。最終的な保証は DB の排他制約 | `RoomSchedule(会議室, 日付)` がその日の予約をすべて持ち、集約の中で重なりを判定する。保存時に版数で衝突を検出する | リクエストごとに「指定区間と重なる予約」を読み込み、それを集約とみなす |
| 同時リクエスト | 排他制約が INSERT のたびにテーブル全体を見て拒否する | 同じ集約の版数を奪い合うので、後から保存した方が失敗する | **防げない**。リクエストごとに読み込む範囲が違い、共通の版数がない |
| 偽の衝突 | 起きない。本当に重なる場合だけ失敗する | 起きる。同じ会議室・同じ日の別の時間帯でも衝突する（再試行で吸収できる） | — |
| 日をまたぐ予約 | 扱える | **扱えない**。2 つの集約にまたがる | 扱える |
| ルールの置き場所 | 集約の外。迂回される恐れがある | 集約の中。迂回できない | — |
| 実装量 | 少ない | やや多い（集約の永続化、楽観ロック、再試行） | — |

C は集約として成り立たない。集約には固定された境界（ID）が必要で、同時に来た更新が同じ単位を奪い合うことでロックが効く。リクエストごとに範囲が変わるものは、集約ではなくただの検索条件であり、仕組みとしては A の事前チェックと同じになる。

## 決定

**A を採用する。**

| 役割 | 担当 |
|---|---|
| 重複しないことの保証 | PostgreSQL の排他制約: `EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)`。`btree_gist` 拡張が必要 |
| 事前チェック（分かりやすいエラーのため） | ドメインの純粋関数 `ReservationPolicy.Reserve`。重なる予約の一覧はハンドラーが読み込んで渡す（ADR-0002） |
| 制約違反の変換 | インフラ層。SQLSTATE `23P01`（exclusion_violation）を捕まえ、ドメインと同じ `ReservationConflict` エラーに変換する |
| API の応答 | ドメインの検出でも DB の検出でも、同じ 409 + ProblemDetails を返す |
| `Reservation` | 集約ルートのまま |

補足:

- 区間は半開区間 `[開始, 終了)` で扱う。10:00〜12:00 と 12:00〜13:00 は重ならない。ドメインの `TimeSlot.Overlaps` も同じ定義にそろえる。
- `Reservation` を生成できる入口は `ReservationPolicy` だけにする（コンストラクタを `internal` にする）。コードでも DB でも、二重に迂回を防ぐ。
- DB で検出した競合は、ユーザーには区別せず見せる。ログ（Warning）とメトリクス（競合の検知件数）でだけ区別する。

### B を見送った理由

B は「集約は整合性の境界」という DDD の原則に最も素直な案だった。しかし、日をまたぐ予約という要件のため、固定の境界（日）を引けない。境界を「会議室」まで広げると、全期間の予約を毎回読み込むことになり重すぎる。粒度が粗いほど無関係な更新同士が衝突するので、集約は小さく保つべきである（Vaughn Vernon「小さな集約を設計せよ」）。

## 結果

良くなること:

- 不変条件の保証が DB に一本化され、同時リクエストに対して確実に守られる。
- 本当に重なるときだけ失敗するので、偽の衝突や再試行のロジックが要らない。
- DB の都合（例外の型、SQLSTATE）がインフラ層で止まり、ドメインや API に漏れない（腐敗防止層）。

受け入れる代償:

- 不変条件の一部が DB スキーマにある。ドメインモデルだけを読んでもルールの全体は分からないので、このADRとテストで補う。
- PostgreSQL 固有の機能に依存する。他の DB に移るときは、制約の再設計が必要になる。
- 排他制約は EF Core の Fluent API で表現できない見込み。Flyway のマイグレーション（SQL）で書く（ADR-0003）。

フォローアップ:

- [ ] 排他制約が同時リクエストで実際に効くことを結合テストで確かめる（2 件を並行して INSERT する）。
- [ ] 境界値をユニットテストで確かめる（ちょうど接する区間、1 分重なる区間、日をまたぐ区間）。
- [ ] `TimeSlot` の上限（例: 最長 24 時間）を決める。上限がないと、1 件の予約で会議室を長期間押さえられてしまう。
- [ ] 時刻の扱い（会議室のタイムゾーン、`timestamptz`）を別の ADR に切り出す。
